## 先看这一页：你到底要交什么

**不是开发插件，不是再生成一万份媒体，不是验证视频能不能播放。**
你要证明两件事：

1. 4.5 生成的一个原始 STRM，Jellyfin 能收录，现有插件确实读到。
2. 用同批文件做少量测试，插件该复用时复用、该要求重新读取媒体信息时作出探测决定，
   八种情况都留下能核对的记录。

| 名词 | 本任务里的简单意思 |
|---|---|
| STRM | 写着媒体地址和可选指纹的小文本文件，不是视频本体 |
| 原始副本 | 从4.5输出原样复制，任何字节都不能改，用来证明生成器产物可被扫描／读取 |
| 标注副本 | 专门用于插件规则测试的STRM，允许按本指南改字段，不能说成生成器直接输出 |
| 基准A | 已保存必要媒体流、插件已有历史、当前地址匹配的一份已知正常状态 |
| 探测 | 插件认为需要重新读取编码、时长等信息；本任务只验决定，不要求这次读取成功 |
| 复用 | 插件明确说继续用已有媒体信息；不是“没看到探测日志” |
| item／source | Jellyfin里的条目／媒体源身份；每行必须指到你正在测的那一个 |

交付顺序只有一条：**核对前置 → 原始副本扫描／读取 → 建正常基准 → 八行逐项验证 →
恢复 → 提交给B。** 一步未满足，不把后面的表格先填成PASS。

## 3. 先交第一件事：原始STRM被扫描、被插件读到（AC-1）

这一步必须用原始字节，不能为了“能访问”先改URL。

1. 核对4.5的 `Plain Movie.strm` 是预期regular文件，记录SHA-256、大小与mtime。
2. 将其不覆盖地复制到本Task的 `original/`。再次算SHA-256，**来源与副本必须相同**。
   来源不存在、已有目标摘要不同或类型不对，就停；不临时手写一份冒充生成器产物。
3. 通过已获准的Jellyfin原生媒体库管理，确认现有库路径，建立或复用只包含该目录的
   专用测试库。不要选择整个 `/strm`、整个媒体目录或10000份输出。
4. 如果原生界面报告与既有库路径重叠、不能隔离，不强行建库／改挂载，报告B处理。
5. 通过该库的原生扫描入口执行扫描，保存当次起止、实际结果、库ID、条目ID与容器路径
   对应。只看“扫描完成”还不够，必须找到这份STRM对应的条目。
6. 通过现有插件原生配置页，仅选择本阶段的专用库；保存原配置的必要字段供恢复。
   再从“计划任务 → STRM 媒体信息检查”执行，保存该条目／source的本次读取／决定日志。
   任务Key为 `StrmProbeOptimizerBatchCheck`；任务ID从当前原生任务列表取得，不能写死旧ID。
   当次执行用起止窗口区分，不假设原生接口还会提供一个独立的每轮run_id。

**已知情况**：原始文件内的 `127.0.0.1:25244` 地址，在Jellyfin容器内此前连接拒绝。
因此这里可以看到缺主流／要求探测或探测失败；如实记录，不改原始字节掩盖它。
本步只证明原始产物扫描和插件读取，不因此宣称媒体可访问、探测成功或比较基准已建立。
如果连条目／插件读取都没有证据，AC-1就未完成，不能用下面标注副本的结果替代。

正常优先走原生界面。若用公开HTTP API，先查当前实例原生API描述或已核对的既有调用，
再记录准确方法、字段和返回ID；不要猜接口，不调用插件内部接口，不访问Jellyfin DB。

## 4. 再建一份能比较的正常基准（AC-2）

这一步改的是 `decision/` 中的**标注副本**，不改 `original/` 或4.5输出。

1. 先验证Jellyfin容器能访问同网络已核对的OpenList稳定入口及这批A内容。可用的候选为
   `http://openlist:5244/d/s3/Plain%20Movie.mkv`；这是已有服务别名和 `/d/` 路径，
   **尚未因为写进指南就成为可达证据**。用本次实际返回的内容与本地A原件核对。
2. 已确认内容一致后，创建标注副本。基准文本为下面四行，UTF-8、换行结束：

```text
# strm-probe-version:1
# strm-probe-sha1:1b7aa9d139d059cdcc579d04e9e36a6b005fcd7e
# strm-probe-size:24404
http://openlist:5244/d/s3/Plain%20Movie.mkv
```

3. 在本次证据中明确写“人工标注测试副本”，记录相对路径、摘要、A原件／固定对象对应。
4. 原生扫描收录这一份副本。原始扫描阶段与矩阵阶段要隔离：可分别使用原生专用库，
   矩阵阶段插件只选择决策库，不反复检查那份已知地址不可达的原始副本或其他历史条目。
   已有合适专用库就复用，不为了每一行重复建库。
5. 通过正常扫描／原生检查或已核对的原生刷新，使该条目有必要主媒体流、当前原生地址
   匹配。执行插件原生检查建立历史，再执行一次不变输入的检查。
6. 只有看到正确item／source明确复用，理由为 `Sha1Matches`，并确认地址与主流条件，
   才把此状态记为“基准A”。保留STRM摘要、服务内容身份、必要媒体流、地址摘要、
   item／source及该次复用日志。不要直接读插件指纹库来“查看／补齐”历史。

**停点**：只看到FirstTrust、只有任务Idle、只有HTTP200、没有必要主流、地址不匹配或
没有逐项决定，都不能进入八行矩阵。正常恢复后仍建不起来，保留失败并报告；不伪造流、
不塞数据库、不直接调用插件函数，不通过播放／代理绕过。

## 5. 八行按这个表做（AC-3／4／5）

每一行都使用同一个决策副本路径，优先保持同一个item／source。开始前确认上一行任务
已经结束、样本已恢复成基准A且明确复用；然后只做本行变化，**不要在变化后先跑一次
刷新／检查把新状态变成历史，再来声称看到了“变化决定”**。

| 行 | 你具体改什么 | 应看到什么 |
|---|---|---|
| D-01 | 什么也不改，再执行一次原生检查 | 明确复用，`Sha1Matches` |
| D-02 | 获准后，同一S3样本用A原字节做同内容写入；确认源端Modified确实变了，内容／Size和STRM字节不变。STRM里不增加Modified | 明确复用，仍为`Sha1Matches`；Modified没变就不能说测了本行 |
| D-03 | 不改URL／服务内容／SHA-1，只把标注副本Size从24404改成24430。这是**刻意的错误大小元数据** | 明确复用，`Sha1Matches`；不能走SizeChanged |
| D-04 | 获准后，将同一S3样本内容A换成已有B，先确认当前同URL实际服务字节是B；副本SHA-1换为B真实值，Size换为24430，URL不变 | 要求探测／`Sha1Changed`；不能拿缺主流或无关地址不匹配充数 |
| D-05 | 在已恢复的A基准上，只把URL换成已核对服务内容同为A的 `http://openlist:5244/d/s3/Synthetic%20001.mkv`；SHA-1与Size不变 | 要求探测，`UrlChanged`，或这次地址变化造成的`NativeUrlMismatch` |
| D-06 | 在A历史上，获准后将同URL服务内容换成B并核对；副本**删掉整行SHA-1字段**，Size设24430，URL不变 | 要求探测／`SizeChanged`；历史侧SHA-1有效，当前侧缺失，两侧有效Size不同 |
| D-07 | 服务内容保持A；副本删掉整行SHA-1字段，Size仍24404，URL不变 | 明确复用／`Unchanged`；历史侧SHA-1有效，当前侧缺失，两侧有效Size相同 |
| D-08 | 服务内容保持A；副本删掉整行SHA-1及整行Size字段，只留版本与URL | 明确复用／`InsufficientFingerprint`；当前侧两字段缺失，不能凭空探测 |

注意：

- D-02／04／06的S3操作必须走新Task获准的渠道，沿用适用的既有S3工具，不另造媒体服务。
  写入前备好A原件与精确对象路径；只操作此已确认样本，不上传整个目录、不改其他对象。
- D-03变的是异常元数据，不是实际媒体大小；报告必须写清。D-04则必须真换内容，不能
  只改一个SHA-1字符串骗过比较。D-06也用同批B，避免大小与服务内容无意不一致。
- D-04／06远端替换后，按正常稳定入口实际观察B；仍看到A就是缓存／可见性尚未满足，
  不开始判行、不强制刷新列表；未知状态停止。恢复时同样先确认实际恢复成A。
- D-06..08用“删整行”表示缺失，不写`null`、`N/A`、全零哈希或零Size冒充缺失。
- 不变行也要有明确复用日志；有探测记录但理由是`MissingPrimaryStream`，说明基准坏了，
  不是哈希／Size分支通过。先恢复，不带病测下一行。
- D-05允许本次URL变化造成地址不匹配；这不是允许所有行都靠地址不匹配通过。
- 某行探测启动后失败，可以记录该行“探测决定匹配／探测结果失败”；**不是把失败写成
  探测成功**。若后续历史／主流不完整，必须先按第4节正常恢复基准，不能直接继续。

### 每行固定做六件事

1. 留基准A的核对记录，确认是这一个item／source，不是另一条目。
2. 保存本行变更前后STRM摘要、字段和必要源端事实。
3. 记准确开始时间，执行一次插件原生检查；等待当次结束，保存结果和结束时间。
4. 从**这个时间窗口、这个item／source**取实际决定；不要用跨几天的全局grep凑证据。
5. 填本行结果，再恢复服务内容和标注副本到A；正常确认主流／地址／历史与明确复用。
6. 保存恢复记录后，才进入下一行。基准身份未变可以复用已核验材料，不能跳过当前核对。

普通日志已包含动作和reason；无需专门开启DetailedLog。探测认明确要求或
`Native STRM probe started`；复用认 `reused saved media information` 且reason匹配。
任务汇总的need probe／skipped数只作辅助，不能代替逐条决定。

## 6. 卡住时只做对应处理，不乱改系统

| 看到的情况 | 正确处理 | 禁止的捷径 |

| 401／403、没有可用凭据 | 记认证BLOCKED，说明准确缺什么 | 查历史密码／Key、读DB、重置账号 |
| 原始URL在容器内连接失败 | 保留原始字节和实际扫描／读取结果；决策副本另建正常基准 | 修改原始URL后声称原始产物直接可达 |
| 只有FirstTrust或缺必要媒体流 | 只算建基准未完成；正常恢复后再核对 | 填D-01 PASS或手写媒体流／指纹 |
| 任务结束但没有当前条目决定 | 查本次库范围、条目对应、时间窗口 | 用无日志证明“没探测”，或开启全库乱跑 |
| 同Hash异Size触发SizeChanged | 查前后有效Hash及历史／source是否真是基准A | 修改插件、降低断言、说“反正发生探测了” |
| 实际理由与本行不对应 | 保留失败，先还原单一变量与正常基准，再重试受影响行 | 把无关MissingPrimaryStream当作Sha1Changed |
| 恢复状态未知或失败 | 停止续验，保存原件／日志并报告 | 继续下一行、重建数据集、清空后重来 |
| 会超过时间预算 | 先停止开启新场景，报告已完成／未运行与必要恢复 | 空等凑比例、删必跑项、伪报完成 |
